# DB 협업과 마이그레이션

기본 DB는 두 개발자가 함께 쓰는 **Supabase PostgreSQL**입니다. 처음 연결할 때는 [Supabase 설정](supabase.md)을 따릅니다.

## 무엇을 공유하나요?

- 실제 행 데이터: 원격 DB에 이미 함께 저장됩니다. Git으로 push/pull하지 않습니다.
- 테이블·컬럼 변경: `db/migrations/0003_설명.sql`처럼 다음 번호의 SQL 파일을 작성하고 Git으로 공유합니다(파일명은 영문 소문자·숫자·밑줄).
- 변경 적용: 최신 코드를 받은 뒤 `npm run db:migrate`. 한 사람이 적용했다면 다른 사람이 다시 실행해도 중복 적용되지 않습니다.
- 같은 계정의 동시 저장: revision이 다르면 409로 거부합니다. 화면을 새로 읽은 다음 다시 편집합니다.

이미 적용한 SQL 파일은 수정하지 않고 새 파일을 추가합니다. 체크섬이 변경되거나 DB가 현재 코드보다 앞선 경우 실행을 중단합니다. 마이그레이션은 트랜잭션과 잠금으로 순서를 보장합니다. 공용 DB 구조를 바꾸면 팀원에게 알려 최신 코드를 받게 합니다.

## 테이블

| 테이블 | 내용 |
| --- | --- |
| `scenelog.archive_owners` | Supabase 사용자 ID, revision, 수정 시각 |
| `scenelog.archive_movies` | 사용자별 영화 메타데이터 |
| `scenelog.viewing_logs` | 별점·관람일·리뷰·테마·티어·재관람 기록 |
| `scenelog.watchlist` | 보고 싶은 영화 |
| `scenelog.schema_migrations` | 적용한 SQL 파일과 체크섬 |
| `scenelog.profiles` | 닉네임, 컬렉션 공개 범위(기본 나만 보기) |
| `scenelog.friendships` | 친구 요청(보낸 사람·받은 사람), 대기/수락 상태 |
| `scenelog.follows` | 과거 팔로우 테이블, 현재 사용하지 않음 |

현재 친구 기능은 `0006_collection_visibility.sql`까지 적용 후 사용할 수 있습니다. 기존 기록 소유자에게 이메일과 무관한 기본 닉네임을 만들며, 새 사용자의 프로필은 로그인 후 프로필·친구 정보를 처음 조회할 때 등록합니다. 회원가입에서 입력한 닉네임은 Auth의 display_name 메타데이터에 저장하고 첫 인증 요청에서 profiles에 초기화합니다. 이후 로그인에서는 설정에서 수정한 닉네임을 덮어쓰지 않습니다. 설정에서 닉네임과 컬렉션 공개 범위를 바꿀 수 있습니다. `GET /api/social`은 닉네임 검색·친구 목록·받은/보낸 요청·친구들의 열람 가능한 기록·프로필 조회, `PUT`은 친구 요청·수락·거절·취소·친구 삭제, `PATCH`는 본인 프로필 설정에 사용합니다. 모두 인증이 필요합니다. 다른 회원의 기록과 통계는 서버에서 공개 범위와 친구 수락 여부를 확인한 뒤 조회하며 찜 목록·개인 다이어리 사진·이메일은 반환하지 않습니다. 목록은 서버에서 10개씩 나눠 조회합니다.

친구 요청은 `PUT /api/social`에 `{ userId, action }`을 보내며 action은 `request`, `accept`, `decline`, `cancel`, `remove`입니다. 요청을 받은 사람만 수락·거절하고 보낸 사람만 취소할 수 있습니다. 수락된 관계는 양쪽의 친구 목록에 나타나며 최근 기록에는 수락한 친구의 열람 가능한 기록만 표시합니다. `0006_collection_visibility.sql`은 공개 범위를 `private`(나만 보기, 기본값), `friends`(수락한 친구만), `public`(모든 회원)으로 나눕니다. 기존 공개 설정은 public, 비공개 설정은 private으로 유지합니다. 검색 통계·프로필·기록·피드 모두 같은 서버 권한 조건을 사용하고 친구 삭제 즉시 이후 조회부터 친구 전용 기록에 접근할 수 없습니다. 동일한 두 사람 사이에는 관계를 하나만 저장하고 트랜잭션 잠금으로 중복 요청을 막습니다. 예전 팔로우는 친구 동의가 아니므로 자동 전환하지 않습니다. 받은 요청 수는 `GET /api/social?tab=summary`로 전체 대기 요청을 집계합니다. 상단 친구들 메뉴와 받은 요청 탭에 동일한 숫자를 표시하고, 수락·거절·취소 뒤 갱신합니다. 다른 기기에서 들어온 요청은 보이는 화면에서 30초마다 또는 창 복귀·새로고침 시 확인합니다.

프로필 사진은 `0004_profile_avatar.sql`의 `profiles.avatar_path`로 연결합니다. `GET /api/profile`로 본인의 닉네임과 사진을 조회하고 `POST /api/profile/avatar`로 사진을 변경하며 `DELETE`로 기본 아이콘으로 돌아갑니다. 닉네임은 Auth 메타데이터 대신 `profiles.display_name`을 공통으로 사용합니다.

사진 파일은 Supabase Storage의 공개 `profile-avatars` 버킷에 저장합니다. 서버의 `SUPABASE_SECRET_KEY`를 설정하고 `npm run storage:setup`으로 버킷을 준비합니다. 같은 키가 배포 환경에도 필요하며 브라우저에는 노출하지 않습니다. 업로드·삭제는 인증된 본인에게만 허용하는 Next API에서 처리하고 브라우저의 직접 쓰기 정책은 추가하지 않습니다. 최대 3MB의 JPG/PNG/WebP를 서버에서 검증하고 384×384 WebP로 변환해 저장합니다. 원본과 EXIF 메타데이터는 보관하지 않습니다. 사진 변경/삭제 시 이전 파일 정리를 시도하며, 정리 실패는 서버의 일반 메시지로 기록합니다.

`0001`은 이미 로컬에 적용한 초기 이력이라 그대로 보존하며 `0002`에서 소유자 컬럼을 `user_id`로 바꿉니다. Firebase의 기존 행을 Supabase 사용자에게 자동 연결하지 않습니다. 계정과 데이터 삭제를 자동 연동하는 `auth.users` 외래 키는 없으므로, 향후 회원 탈퇴 API에서 기록 삭제도 처리해야 합니다.

Next.js가 인증된 ID로 SQL의 소유자를 제한합니다. 공유 DB에서 개발한다는 것은 같은 DB 인스턴스를 쓴다는 뜻이며, 앱에서 다른 이용자의 개인 기록을 볼 수 있다는 뜻은 아닙니다. DB 관리자 권한으로는 행을 조회할 수 있습니다. 현재 개발 연결은 테이블 소유자 권한을 사용하므로 운영 전용 계정·권한 분리는 배포 시 별도로 구성합니다.

## 명령어와 검증

기록 추가·수정·티어 변경은 `PUT /api/archive/log`로 `{ movie, log, revision }` 한 건만 전송합니다. 서버는 인증된 사용자의 행을 잠근 뒤 revision을 확인하고, 해당 영화 정보와 관람 기록만 upsert합니다. 해당 영화의 찜 해제와 revision 증가도 같은 트랜잭션으로 처리합니다. 응답에는 저장된 한 건과 새 revision만 포함하며, 브라우저는 기존 목록에 이를 반영합니다. 기존 테이블을 사용하므로 추가 마이그레이션은 없습니다.

찜 추가·삭제는 `PUT /api/archive/watchlist`에 `{ saved: true, movie, revision }` 또는 `{ saved: false, movieId, revision }`을 보냅니다. 해당 찜만 반영하며, 찜 해제 시 관람 기록이 없는 영화 메타데이터만 함께 정리합니다. 관람 기록과 다른 영화의 찜은 유지합니다.

`GET /api/archive`는 최초 조회에 사용합니다. 기존 `PUT /api/archive`의 전체 교체 API는 호환성을 위해 유지하며, 단건 API와 같은 revision으로 충돌을 검사합니다. 컬렉션 페이지네이션은 현재 클라이언트에서 표시할 카드 수를 제한합니다.

```bash
npm run db:setup     # 마이그레이션 + 연결 확인
npm run db:migrate   # 아직 적용하지 않은 파일 적용
npm run db:check     # 연결과 스키마 상태 확인
npm test            # 외부 서비스 없이 PostgreSQL SQL/인증/API 회귀 테스트
```

DB 오류는 원본 연결 URL이나 비밀번호를 출력하지 않습니다. 인증서 오류는 인증서 구성을 확인하고, 연결 오류는 pooler URI·DB 비밀번호·프로젝트 상태를 확인하세요. API 401은 로그인 상태, 503은 Auth/DB 연결 설정을 확인합니다.

## 선택 사항: 독립 로컬 DB

네트워크 없이 DB 작업을 하거나 실제 다중 연결 테스트를 할 때만 사용합니다. 기본 협업에는 필요 없습니다. macOS에서는 PostgreSQL 18을 설치한 뒤 `npm run db:local:setup`을 사용할 수 있습니다. **이 명령은 .env.local의 DB URL을 로컬로 바꾸므로 공유 DB 개발 중에는 실행하지 마세요.**

`db:start`, `db:stop`, `db:status`는 `.local/postgres`의 로컬 DB만 관리합니다. `db:test`는 `127.0.0.1:55432/scenelog`에서만 실행되며 공용 DB 테스트로 사용하지 않습니다. DB를 종료해도 파일은 유지합니다.


## 칭호와 도전과제

`0007_achievements.sql`은 `profiles.equipped_title`, `user_achievements` 및 가입 프로필의 기본 칭호 트리거를 추가합니다. 기존 프로필에도 `first-seat`가 지급됩니다. `GET /api/achievements`는 인증된 본인의 저장 기록으로 달성을 확정하고, `PUT`은 획득한 칭호만 장착합니다. 이미 획득한 칭호는 기록을 수정해도 유지됩니다. 개인별 진행도는 본인에게만 반환합니다.

카탈로그는 `src/lib/achievements.ts`에서 관리합니다. 공개한 ID는 바꾸지 않습니다. 현재 158개이며 누적 영화 수, 14개 장르, 감상, 세부 평가, 관람일, 재관람, 관람 월, 연속 관람 월을 지원합니다. 영화 수는 고유 영화, 월별 기록은 실제 관람일로 집계하며 미래 관람일은 제외합니다. 연속 월은 연도를 넘어 이어진 가장 긴 구간입니다. 1,000·1,500·2,000편은 황금 장식입니다. 카탈로그 확장에는 추가 DB 마이그레이션이 필요하지 않습니다.

보유율은 `user_achievements`의 확정된 획득 회원 수 / `profiles`의 전체 회원 수입니다. 프로필이 아직 생성되지 않은 Auth 계정과 도전과제 조회 전 미확정 달성은 분모/분자에 각각 포함하지 않으며 화면에 기준을 명시합니다. 장착 여부는 비율에 영향을 주지 않습니다. 집계 한 문장에서 분모·분자를 읽어 일관된 시점을 사용하고, 타인의 기록이나 ID는 응답에 포함하지 않습니다. 원래부터 Auth 삭제와 프로필 삭제는 자동 연동되지 않으므로 탈퇴 처리는 프로필도 삭제해야 합니다.

계정별 누적 영화·관람 기록·찜 개수에는 앱이 정한 상한을 두지 않습니다. 저장 시 전체 개수 조회/차단도 하지 않습니다. 일반 기록 저장·수정과 찜 추가·삭제는 단건 요청으로 처리하므로 누적 데이터량과 요청 크기가 무관합니다. 한 번의 전송 크기는 단건 64KB, 기존 전체 교체 API 4MB이며, 계정 저장 용량 제한이 아닙니다. 전체 교체 API는 큰 아카이브를 한 번에 가져오는 용도로 사용하면 안 됩니다. 도전과제 목록은 24개씩 표시하며, 검색·분류로 범위를 좁힙니다. 장식은 CSS로 표현하고 미리보기/프로필 애니메이션은 유한 반복하며 동작 줄이기 설정을 따릅니다.

도전과제 응답에는 카탈로그 지문(`catalogVersion`)을 포함하고, 브라우저와 서버의 정의가 다르면 새로고침 안내를 표시합니다. 획득/전체 개수는 같은 응답 목록으로 계산합니다. 첫 조회에는 칭호 미리보기를 먼저 렌더링하며, 계정별 메모리 캐시는 30초 동안 재사용하고 기록 변경 시 무효화합니다. 오래된 캐시를 보여주면서 갱신할 수 있지만 5분이 지나면 폐기합니다. 인증 세션 갱신을 포함한 클라이언트 요청에는 12초 대기 한도를 둡니다. 서버 처리는 프로필 잠금·진행도 조회 및 획득·장착·보유율 집계를 두 개의 처리 쿼리로 묶습니다(BEGIN/COMMIT 포함 네 번 왕복).

장르 칭호는 10편부터 동색, 50편부터 은색, 100편부터 금색 마감을 사용합니다. 기존 30편 칭호는 동색 월계수 단계로 유지하며 14개 장르에 50편 칭호를 추가했습니다. 금색은 장르 고유 아이콘과 왕관 프레임, 정적인 방사형 후광을 사용합니다. 프로필·상세 미리보기의 후광만 3회 은은하게 변화하고 동작 줄이기 설정에서는 정지합니다.
